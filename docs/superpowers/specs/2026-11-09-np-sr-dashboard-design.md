## 1. Зачем

Автор — руководитель направления «новые продажи сервисов» (НП СР) в компании. Каждое утро автор открывает 8 Excel-отчётов из сетевых папок, ищет свои
6 групп, смотрит текущую неделю («компания живёт неделями», сейчас 45-я), раскрывает до вчерашнего дня,
находит «гадких утят» среди групп, проваливается до сотрудников и идёт к руководителю группы
(РГ): «вот эти люди, вот этот показатель, вот что делать». Динамику показателей он держит в голове — это
и есть боль.

Цель: один дашборд, где **одним взглядом** видно, в чём каждая группа сильна и где отстаёт; оттуда — провал
в группу и до сотрудников. Ссылку на дашборд получают все РГ, каждая группа сама видит своих «утят».

## 2. Цели, не-цели, анти-цели

**Цели**
- Главный экран: картина по направлению → по группам → провал в группу → сотрудники.
- Автоматическая подсветка «хорошо / зона риска / гадкий утёнок / эталон» по правилам §5.
- Сбор отчётов в один клик из сетевых папок, публикация на GitHub Pages в зашифрованном виде.
- Накопление собственной истории (снимки по дням); на дашборде — окно 4 недели, включая текущую.
- Редактируемые нормативы.

**Не-цели**
- Персональные доступы, роли, «моя группа» с запоминанием — не нужны: все РГ видят всё (данные и так
  открыто рассылаются в группу). Только кнопки провала в любую группу.
- Показ групп «Ученики», «СР4_Упр», «КЦПК_НП_СР_Москва» и других направлений — никогда.
- Редактирование данных руками, комментарии, задачи/инструкции РГ внутри дашборда.

**Анти-цели (провал, даже если «работает»)**
- Исходные Excel, сырые строки, номера телефонов, ПИНы клиентов, суммы сделок по клиентам попадают в
  публичный репозиторий — в любом виде, включая историю git.
- Утренний процесс у автора остаётся многошаговым (искать файлы, копировать, запускать скрипты в консоли).
- Цвета врут: вся группа красная из-за «холодного» дня, когда просели все.
- Выглядит как шаблонная админка. Автор хочет «шикарно».

| СР1 | `КЦПК_НП_СР_Тверь_СР1_ГБ` |

Сотрудник «в штате на дату» = на нём есть план в дневной воронке на эту дату. Удельные показатели
«на человека» считаются по штату на дату.

Неделя — как в отчётах компании (`2026.45`); отчёты собираются «по вчерашний день».

Правило сверки: для каждого показателя, где в отчёте есть готовая сводная, посчитанное парсером значение
по группе за неделю должно совпасть со сводной (это и есть тест парсера).

Отдельного листа «Попытки» в ГкГ нет — попытки в НС = лист «Звонков на цепочку длит» (подтверждено автором).
Блок НС автор, возможно, позже переведёт на другой отчёт по НС1 — парсер этого показателя должен быть
заменяемым.

**Гранулярность [моё решение].** Часть показателей есть по дням (Опер_отчет, воронка, ОЗ, ПИНы), часть —
только по неделям (ГкГ, 300+, АК). В режиме «вчера» недельные показатели показывают значение текущей недели
с пометкой «неделя»; в графике сотрудника по дням рисуются ступеньками по неделям.

**Свежесть [моё решение].** «Вчера» = последний рабочий день (в понедельник — пятница). Для каждого отчёта
в конфиге админки — допустимое отставание в рабочих днях (по умолчанию 1); пометка «устарел» только при
превышении. Дата данных берётся из содержимого отчёта, а не из имени файла.

**Старт истории [моё решение].** История копится с первого сбора; дневная воронка содержит только текущий
месяц, поэтому в первые недели часть графиков короче 4 недель. Разовая подгрузка архивных файлов — через
ручное перетаскивание (тот же путь, что и запасной), отдельный режим не нужен.

## 5. Оценка «хорошо / плохо»

Два слоя, применяются по порядку:

1. **Абсолютный норматив → зона риска.** Значение ниже норматива — жёлтое «зона риска». Норматив сравнивается
   с **накопленным итогом недели** (дневные колебания — пятница ниже понедельника — не должны красить
   ячейки жёлтым каждый день) **[моё решение]**.
2. **Относительное сравнение → «гадкий утёнок».** Красное, если значение хуже среднего по группам направления
   (для сотрудников — по сотрудникам направления) **более чем на 15%** за тот же период. Порог редактируемый
   **[моё решение]**. Так «холодный» предпраздничный день, где просели все, не делает красными всех.
3. **Эталон.** Лучшая группа по показателю обводится как эталон («красавчики»).
4. Для показателей без абсолютного норматива (АК, свод по заказам, взятые) — только слои 2 и 3; ниже
   среднего, но в пределах 15% — жёлтый.
5. Ран-рейт — четыре ступени: <100, 100, 120, 140 (подписи «круто / супер / отличный кайф»).

Все нормативы и порог 15% редактируются в админке и публикуются вместе с данными.

## 6. Фронтенд (дашборд)

Выбранный макет: `.superpowers/brainstorm/*/content/layout.html`, варианты А + Б.

- **Главный экран:** выбор недели (по умолчанию текущая, доступны 4 недели) и дня («вчера» по умолчанию,
  либо «вся неделя»). Сверху — крупный ран-рейт направления по деньгам (кольцо), под ним меньшее кольцо по штукам, и 3–4 главных
показателя. Ниже —
  кнопки **«Рейтинг руководителей»** и **«Данные для ДПП, координатора и РФ»** (панель с показателями
  для руководства), затем **тепловая карта** «6 групп × показатели» + строка «направление».
  Ниже — **карточки групп** (паспорт: кольцо ран-рейта, «N сильных / N в риске / N провалов» — плашки
  кликабельны и раскрывают список показателей зоны, полоски показателей против черты норматива). Клик по
  названию группы (строка или карточка) — экран группы.
- **Рейтинг руководителей:** лесенка групп — место, кольцо ран-рейта, группа, качественные показатели.
  Место: больше сильных → меньше провалов → ближе к цели. Учитываются ран-рейт, качественные счета,
  длинные презентации, попытки НС1 / 300+ / ОЗ, ОЗ за 30 минут, сроки оплаты (первичка и НС); взятые и
  завершённые — нет.
- **Экран группы:** паспорт группы покрупнее + такая же тепловая карта, где строки — сотрудники группы.
  Клик по ячейке — динамика этого показателя у сотрудника по дням (4 недели), с линией норматива.
  **Фильтр сотрудников:** «Скрыть тех, у кого нет плана в дневной воронке», ручной выбор, «Показать всех»;
  цифры группы пересчитываются без скрытых; фильтр хранится в браузере зрителя.
- Кнопки всех 6 групп всегда доступны.
- Где показателя нет (СР9 в части отчётов) — прочерк, без окраски и без ошибки.
- Плашка «данные за <дата>, обновлено <время>»; если отчёт устарел (не за вчера) — пометка на его
  показателях.
- Вид: светлый, белые карточки, мягкие тона. Палитра — мягкие версии фирменных красного/белого/чёрного +
  зелёный («Проверка контрагентов») и синий. Красный — только для «утят», не для декора. Шрифт с хорошей
  кириллицей (в макете — Onest). Референс автора: светлый дашборд с карточками, кольцами, плавными графиками.
  Должен работать на телефоне (РГ откроют ссылку с телефона) **[моё решение]**.

## 7. Админка (локальная, на компьютере автора)

- Запуск двойным кликом по ярлыку; открывается в браузере, работает только на `localhost`.
- **Первая настройка:** для каждого из 8 отчётов — путь к сетевой папке (и шаблон имени файла). Пути
  сохраняются; при следующем запуске подставлены.
- **«Собрать отчёты»:** в каждой папке находит самый свежий файл по шаблону, копирует к себе, парсит,
  показывает сводку: какой файл, за какую дату данные, что подтянулось, предупреждения (отчёт не за вчера,
  нет группы, не сошлась сверка). Запасной путь — перетащить файлы руками (нет сети/VPN).
- **«Опубликовать»:** шифрует и публикует на GitHub Pages. Первое время публикация — отдельной кнопкой после
  просмотра сводки; позже можно склеить в одну кнопку **[моё решение]**.
- **История:** после каждого сбора админка сохраняет снимок посчитанных показателей по дням у себя
  локально (вне репозитория). Публикуется окно 4 недели, включая текущую. Если в новом отчёте за прошедший
  день данные изменились — новый снимок перекрывает старый.
- **Нормативы:** редактируемая таблица (§4–5).
- **Ссылка:** генерация кодовой фразы и ссылки `https://konturproject.github.io/pulse-board/#/?k=<фраза>`;
  смена фразы сразу перешифровывает и публикует данные. Публикация — только из ветки `main`.
- **Обновление программы:** `git pull` в папке проекта (Git Bash), затем перезапуск админки.

## 8. Шифрование и публикация

Повторяем схему Stepper Game (`stepper game/src/data/crypto.ts`, решения D-12, D-33, SEC-6..10 в его
`docs/`):
- AES-GCM 256, ключ — PBKDF2-SHA-256, 250 000 итераций, от кодовой фразы. Конверт `*.enc.json` =
  `{v, alg, kdf, iter, salt, iv, ciphertext}` — совместим с WebCrypto в браузере.
- Фраза — в ссылке после `#` (не уходит на сервер), после первого открытия сохраняется в localStorage и
  убирается из адресной строки. Без фразы — экран «Введите код доступа».
- Фраза — несколько простых слов латиницей + цифры (как `src/admin/words.ts` Stepper).
- Публичный репозиторий на аккаунте `KonturProject` (на нём уже Stepper / sales-quest, `gh` авторизован).
  Имя репозитория нейтральное, без названия компании **[моё решение]**.
- В репозитории никогда: Excel-файлы, сырые строки, локальная история, конфиг с путями. Рабочая папка
  проекта сейчас содержит исходные отчёты — `.gitignore` и проверка перед публикацией обязаны это
  отсекать.
- Это защита от случайного доступа из интернета, не от сотрудников со ссылкой; при утечке ссылки —
  смена фразы (старые коммиты остаются зашифрованы старой фразой).

## 9. Ограничения

- Windows 10, Python 3.14 и Node есть; `pyxlsb`, `openpyxl`, `pandas` установлены.
- Файлы большие (до 115 МБ `.xlsb`, листы до 1 млн строк) — парсинг только локально, не в браузере;
  сбор может занимать минуты — нужен видимый прогресс.
- Отчёты — сводные таблицы с фильтрами и «плавающей» шапкой: парсер ищет заголовки по тексту, а не по
  фиксированным координатам.

## 10. Оставлено строителю

- Технологии фронтенда и админки (с учётом: парсинг xlsb надёжнее в Python; крипто-модуль Stepper на TS
  можно переиспользовать во фронтенде), библиотека графиков, схема файлов данных, способ публикации
  (git push или GitHub API), структура локального хранилища снимков.
- Точные столбцы в каждом отчёте — по образцам в корне проекта, с тестом-сверкой против готовых сводных.
