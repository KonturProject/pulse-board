# Пульс направления — описание проекта

Актуально на 11.11.2026. Документ описывает, **как проект устроен сейчас**. История решений —
в `docs/superpowers/specs/` (дизайн) и `docs/superpowers/plans/` (план первого запуска).

---

## 1. Что это и зачем

Единый дашборд для руководителей групп направления продаж. Раньше координатор каждое утро открывал
8 Excel-отчётов из сетевых папок, искал свои 6 групп, раскрывал отчёты до вчерашнего дня, держал динамику в
голове и ходил к руководителям групп (РГ) с выводами. Теперь:

- координатор **в один клик собирает** все отчёты и **публикует** зашифрованные показатели на сайт;
- руководители групп открывают **одну ссылку** и одним взглядом видят, в чём их группа сильна, где
  отстаёт, кто из сотрудников «проседает», и как группа выглядит среди соседей.

Проект состоит из двух частей:

| Часть | Где работает | Что делает |
|---|---|---|
| **Админка** (`admin/`) | только на компьютере координатора, `http://127.0.0.1:8765` | собирает отчёты из сетевых папок, считает показатели, копит историю, шифрует и публикует |
| **Дашборд** (`web/`) | GitHub Pages, https://konturproject.github.io/pulse-board/ | расшифровывает данные по коду из ссылки и показывает экраны |

Сырые отчёты и история никогда не покидают компьютер координатора. На сайт уходит только один
зашифрованный файл с уже посчитанными показателями.

## 2. Группы и область данных

Шесть групп направления, один филиал (Тверь; СР5 формально тоже в Твери, разбивки по филиалам нет):

| Ключ | Название на экране | Как пишется в отчётах |
|---|---|---|
| СР1 | СР1 ГБ | `КЦПК_НП_СР_Тверь_СР1_ГБ` |
| СР2 | СР2 Фин | `КЦПК_НП_СР_Тверь_СР2_Фин` |
| СР3 | СР3 ГБ | `КЦПК_НП_СР_Тверь_СР3_ГБ` |
| СР5 | СР5 ГБ УД | `АП_НП_СР_Москва_СР5_ГБ_УД` |
| СР6 | СР6 Право | `КЦПК_НП_СР_Тверь_СР6_Право` |
| СР9 | СР9 ГБА | `КЦПК_НП_СР_Тверь_СР9_ГБА` (в части отчётов её нет — это норма) |

Никогда не показываются: «Ученики», закрытые СР4 Упр и «КЦПК_НП_СР_Москва» (они участвуют только как база
прошлого года в сравнении «год к году»), группы других направлений. Справочник — `admin/npsr_admin/groups.py`.

Неделя — ISO-неделя в формате отчётов (`2026.45`). Отчёты собираются «по вчерашний день»; «вчера» —
последний рабочий день (в понедельник это пятница).

Сотрудник «в штате на день» — у него есть план в дневной воронке на этот день. По штату считаются все
показатели «на человека».

## 3. Отчёты и показатели

Админка читает 8 отчётов. Для каждого есть свой парсер в `admin/npsr_admin/parsers/`, и для каждого
показателя, у которого в отчёте есть готовая сводная, тест сверяет посчитанное со сводной.

| Показатель | Отчёт (шаблон имени) | Как считается | Уровень | Норматив по умолчанию |
|---|---|---|---|---|
| **Ран-рейт, деньги** (и штуки) | `Опер_отчет_*.xlsb` | месячный % выполнения плана на дату нарастающим итогом: факт с 1-го числа / план с 1-го числа | день, сотрудник | <100% риск; 100 «круто», 120 «супер», 140 «отличный кайф» |
| **Качественные счета на чел.** | `АП_НП_СР_Воронка_Дни*.xlsx` | «Качественные счета, шт.» / дни в штате | день, сотрудник | цель 4 |
| **Длинные презентации на чел.** | то же | «Разговоры от 20 минут, шт.» / дни в штате | день, сотрудник | ниже 1,2 — провал, ниже 1,5 — риск |
| **Взятые, % плана** | то же | факт «Взятые» / план «Взятые» | день, сотрудник | от среднего по группам |
| **Попытки в НС1** | `АП_НП_СР_Воронка_ГкГ_НС*.xlsb` | `num_dur / over_fact_traf` по кампаниям НС1 — читается **из кэша сводной** (см. §6) | неделя, сотрудник; прошлый год — по группам и направлению | цель 5 |
| **Попытки в 300+** | `*Попытки в 300+*.xlsx` | «Кол-во перезвонов» / «Кол-во звонков» | неделя, группа | цель 3,8 |
| **Попытки в ОЗ** | `АП_НП_СР_Попытки в первичке ПИНы_ОЗ*.xlsx` | среднее «Кол_во_перезвонов» на ПИН: кампания «Обратный звонок/Онлайн-заявка», «Нужно ли делать >1 попытки» = «Нужно» | день, сотрудник | цель 6,5 |
| **ОЗ взяты за 30 минут** | `АП_НП_Обратный звонок_new*.xlsm` | как в сводной «New»: (`WORKED_IN_TIME_DAY_2_DAY` + `WORKED_IN_TIME_DAY_2_DAY_30`) / `CALLS`; типы событий 66661, 777771–777774; девять издательских групп сводной; «можно звонить в этот день» = 1 | день, сотрудник | цель 95% |
| **АК: срок оплаты, первичка / НС** | `АП_НП_СР_АК*.xlsb` | доля оценок «100» по критерию «7.1. Сроки оплаты» (карта «АП_МП_Оценка робота») / «3. Срок оплаты» (карта «Оценка робота_НС_new») | неделя, сотрудник | от среднего |
| **АК: обратная связь руководителя** | то же | средний балл карты «АП_ОС_Практика_РГ 2.0» — оценка самого РГ | неделя, группа | от среднего; **только в панели для руководства** |
| **Счета на доп. места / школы / периодику на чел.** | `АП_Свод_по_заказам*.xlsb` | число счетов из листов «НП СР допместа», «НП СР РС Школы», «НП СР РС Периодика» / штат группы за неделю | неделя, группа | от среднего |

Сверки, закреплённые тестами (на образцах отчётов из корня проекта):

- ран-рейт по штукам у направления = «% вып на дату» листа «Свод»;
- качественные счета группы за неделю = итоговая строка группы в воронке;
- попытки 300+ = «Общий итог» сводной; попытки ОЗ = 140 ПИНов и 6,586 за 45-ю неделю;
- ОЗ за 30 минут: 277 из 280 = 98,9%, как в сводной «New»;
- попытки НС1: 1155 / 256 = 4,5117 (текущий год без СР9, как в сводной) и 3,4523 (прошлый год);
- счета свода по заказам = «Общий итог» каждого листа.

Убрано по решению координатора: «АК: охват оценкой робота» — показатель ничего не различал.

## 4. Как красится «хорошо / плохо»

Каждая ячейка получает зону. Правила применяются по порядку (`web/src/eval.ts`):

1. **Гадкий утёнок (красный)** — значение хуже среднего по группам **больше чем на 15%** (для сотрудников —
   по всем сотрудникам направления), либо ниже «минимума» показателя (у длинных презентаций — 1,2).
2. **Зона риска (жёлтый)** — ниже цели. Цель сравнивается с **накопленным итогом недели**, а не с одним днём:
   пятница ниже понедельника не должна красить всё жёлтым. Без цели — ниже среднего по группам.
3. **Хорошо (зелёный)** — всё остальное. **Эталон** — лучшая группа по показателю, обведена зелёной рамкой.

Холодный день, когда просели все, не делает всех красными: «утёнок» определяется относительно соседей.
Цели, минимумы и порог 15% редактируются в админке и уезжают на сайт со следующей публикацией.

## 5. Экраны дашборда

**Главный экран** (`#/`)
- Выбор недели (4 последние) и дня (по умолчанию — день последних данных) или «Вся неделя».
- Кольцо ран-рейта направления по деньгам, рядом меньшее — по штукам; ключевые показатели с целями.
- Кнопки **«Рейтинг руководителей»** и **«Данные для ДПП, координатора и РФ»**.
- Тепловая карта «6 групп × показатели» + строка «Направление». Недельные показатели в режиме дня
  помечены «нед.». Устаревший отчёт — значок ⚠ в шапке его колонок.
- Карточки групп: кольцо ран-рейта, полоски против цели и плашки «N сильных / N в риске / N провалов».
  **Плашки кликабельны** — раскрывают список показателей этой зоны со значением и целью.

**Данные для ДПП, координатора и РФ** (панель на главном экране) — показатели для руководства, которые
группам смотреть не обязательно: сейчас это аудиоконтроль обратной связи РГ. Это «убрано с глаз», а не
закрыто: код доступа у всех один.

**Рейтинг руководителей** (`#/rating`) — лесенка групп по качеству работы. Учитываются ран-рейт и
качественные показатели (качественные счета, длинные презентации, попытки НС1 / 300+ / ОЗ, ОЗ за 30 минут,
сроки оплаты в первичке и НС). Объёмы воронки (взятые, завершённые) не учитываются. Место:
больше сильных → при равенстве меньше провалов → при равенстве ближе к цели в среднем
(`web/src/rating.ts`).

**Экран группы** (`#/g/СР1` …)
- Паспорт группы, переключатель всех 6 групп.
- Тепловая карта сотрудников (показатели, которые есть по людям). Клик по ячейке — график сотрудника за
  4 недели с линией цели и средним группы.
- **Фильтр сотрудников:** кнопка «Скрыть тех, у кого нет плана в дневной воронке», ручной выбор галочками,
  «Показать всех». Цифры группы (паспорт, полоски, сравнение) пересчитываются без скрытых людей из
  частей расчёта по каждому сотруднику. Фильтр запоминается в браузере каждого зрителя и никому больше
  не виден.

**Экран доступа** — если открыть сайт без кода или с неверным кодом. Код из ссылки сохраняется в браузере
и убирается из адресной строки; при сбое сети он не стирается.

## 6. Как устроена админка

```
Сетевые папки ──► collect.py ──► parsers/* ──► Fact(метрика, период, группа, сотрудник, числитель, знаменатель)
                                                      │
                                    store.py (SQLite-история, %LOCALAPPDATA%\npsr-dashboard)
                                                      │
                                aggregate.py ──► payload (4 недели, значения + части по сотрудникам + штат)
                                                      │
                     publish.py: crypto.py (AES-GCM) ──► web/public/data/*.json ──► git push ──► GitHub Pages
```

- **Факты «числитель / знаменатель».** Любой показатель на любом уровне = сумма числителей / сумма
  знаменателей. Поэтому доли, средние «на человека» и % плана корректно складываются от сотрудника к
  группе и направлению.
- **История.** Каждый сбор заменяет факты источника по тем (показатель, период), что он принёс; пустой
  результат ничего не стирает; старый (архивный) файл не сдвигает дату свежести назад.
- **Свежесть.** Дата данных берётся из содержимого отчёта (у недельных — по дате файла). Отчёт старше
  допустимого отставания (по умолчанию 1 рабочий день) помечается на сайте.
- **Кэш сводных (`pivot_cache.py`).** Внутри `.xlsb` Excel хранит все исходные строки сводной таблицы.
  Админка читает их напрямую (двоичный формат MS-XLSB), поэтому ей не мешают защита листа, режим «только
  чтение» и свёрнутые уровни. Так считаются попытки в НС1 до каждого сотрудника; формула вычисляемого поля
  берётся из самого кэша.
- **Устойчивость.** Шапки сводных ищутся по тексту, а не по координатам; ошибка одного отчёта не
  останавливает остальные; отчёт, давший 0 записей, помечается предупреждением, а его старые данные не
  стираются.
- **Сервер админки** слушает только `127.0.0.1`, отклоняет чужой `Host` и запросы с других сайтов
  (защита от подделки запросов).
- **Публикация** возможна только из ветки `main` (с неё собирается сайт). Смена кода доступа сразу
  перешифровывает и публикует данные.

Локальное состояние админки — `%LOCALAPPDATA%\npsr-dashboard`:
`config.json` (папки, шаблоны, нормативы, код доступа, адрес сайта), `history.sqlite` (история),
`cache\` и `uploads\` (копии отчётов). Эту папку нужно переносить при смене компьютера — иначе
появится новый код доступа и пропадёт история.

## 7. Безопасность

- Публичный репозиторий содержит только код и два файла данных: зашифрованный
  `web/public/data/dashboard.enc.json` и открытый `version.json` (отпечаток и время).
- Шифрование: AES-GCM 256, ключ — PBKDF2-SHA-256 (250 000 итераций) от кода доступа. Код — 4 слова и 2 цифры.
- Код передаётся в ссылке после `#` — эта часть адреса не уходит на сервер.
- Excel-файлы, история, конфиг не попадают в git: `.gitignore` + `scripts/check_public.py` в хуке перед
  коммитом и в CI.
- В публичных файлах нет названия компании, имени директора и фамилий сотрудников. Перед каждым
  `git push` изменения проверяются на имена.
- Это защита от случайного доступа из интернета, а не от сотрудников со ссылкой. Если ссылка утекла —
  «Сменить код доступа» в админке и разослать новую ссылку.

## 8. Работа с проектом

**Каждое утро (координатор):** «Запустить админку.bat» → «Собрать отчёты» → проверить сводку →
«Опубликовать». Через 1–2 минуты сайт обновлён.

**Обновить программу на рабочем компьютере:** в папке проекта правой кнопкой → «Open Git Bash here» →
`git pull` → перезапустить админку → собрать и опубликовать.

**Перенести на новый компьютер:** Python 3.12+ (для текущего пользователя, с «Add to PATH»), GitHub Desktop
или PortableGit, `git clone https://github.com/KonturProject/pulse-board.git`, скопировать
`%LOCALAPPDATA%\npsr-dashboard`, запустить «Запустить админку.bat» (первый запуск сам поставит библиотеки).

**Добавить новый отчёт:** парсер в `admin/npsr_admin/parsers/` (функция `parse(path) -> ParseResult`),
регистрация в `parsers/__init__.py`, шаблон имени в `config.py`, показатель в `web/src/metrics.ts`
(и при необходимости в `RATING_METRICS`). Экраны переделывать не нужно.

**Тесты:**

```bash
cd admin && .venv/Scripts/python -m pytest -q    # админка и парсеры; сверки работают при образцах отчётов в корне
cd web && npm test && npm run build               # дашборд
```

GitHub Actions на каждый пуш в `main`: проверка запрещённых файлов → тесты → сборка → выкладка на Pages.

## 9. Структура репозитория

```
admin/npsr_admin/
  parsers/        — по парсеру на отчёт (oper, funnel_days, gkg, attempts300, ak, orders, oz_speed, oz_attempts)
  pivot_cache.py  — чтение кэша сводных из .xlsb
  excel.py        — потоковое чтение xlsx/xlsm/xlsb, поиск шапок по тексту
  model.py, groups.py, weeks.py — факты, справочник групп, недели
  store.py, aggregate.py         — история и сборка данных для сайта
  crypto.py, phrase.py, publish.py — шифрование, код доступа, публикация
  collect.py, config.py, server.py, ui/ — сбор отчётов, настройки, веб-интерфейс админки
web/src/
  App.tsx, route.ts, access.tsx, data.ts, crypto.ts — загрузка, доступ, маршруты
  eval.ts, view.ts, metrics.ts, format.ts          — зоны, выбор значений, список показателей
  rating.ts, adjust.ts                              — рейтинг; пересчёт группы без скрытых людей
  screens/ (Main, Group, Rating), ui/ (Heatmap, GroupCard, Ring, Trend, Header)
scripts/check_public.py — запрет Excel и локального состояния в git
Запустить админку.bat   — запуск админки (первый запуск ставит окружение)
```
